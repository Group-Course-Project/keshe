# 面向西安市初中毕业生的中考志愿智能分析推荐系统 · 项目方案（V0.1）

> 本文件是与用户共同探索的第一版方案，用于统一认知、固定范围、确定技术路线。
> 后续每一轮讨论都以本文件为准，有变更就在对应章节追加「变更记录」。

## 1. 一句话定位

一个面向西安市初中毕业生及家长的中考志愿填报 Web 应用：
以「近五年录取位次投档数据」为知识库，通过「考生画像 + 位次冲稳保 + 大模型分析报告」三步，
把志愿填报从「拍脑袋」变成「有数据、有依据、可解释」的决策辅助。

## 2. 目标用户与核心价值

- 目标用户：西安市应届初中毕业生、家长、班主任/学校升学指导老师。
- 核心痛点：信息不对称——考生不知道自己的分数/位次能上什么学校，也不理解各校历年波动。
- 核心价值：
  1. 数据可视化：用 ECharts 展示目标学校近五年录取位次趋势。
  2. 可解释推荐：给出「冲 / 稳 / 保」三档候选学校，并说明计算依据。
  3. 个性化报告：大模型把结构化结果转成家长/考生能读懂的填报分析。
  4. 风险校验：模拟志愿表用贪心算法校验梯度是否合理，降低滑档风险。

## 3. 功能拆解（对应项目的三步）

### 第一步：数据采集与知识库

- 输入：西安市近五年（如 2021–2025）各高中招生计划、录取最低分、最低位次、住宿、所属城区、办学性质等。
- 处理：清洗（单位统一、缺失补全、异常值剔除）、标准化（位次统一为全市/城区口径）、入库。
- 产出：
  - `school` 学校专业库（基本信息、标签、住宿、城区）。
  - `enrollment_record` 历年投档记录（年份、计划数、最低分、最低位次、平均分等）。
  - 位次趋势可查询接口（供 ECharts 使用）。

### 第二步：画像过滤 + 匹配评分 + 冲稳保

- 考生画像：位次/预估位次、目标城区、是否要求住宿、学校性质偏好（公办/民办）、学校类型偏好等。
- 硬性过滤：不满足「提供住宿 / 所选城区 / 学校性质」等选项的学校直接剔除。
- 匹配分数：综合「位次匹配度、城区契合度、住宿契合度、历年稳定性、热度/竞争度」加权得到 `match_score`。
- 冲稳保计算：
  - 冲：录取位次略高于考生位次（风险偏好）。
  - 稳：录取位次与考生位次接近。
  - 保：录取位次明显低于考生位次（安全垫）。
  - 规则先做成可配置的阈值（如 ±N 位次百分比），后续用历史数据回测校准。

### 第三步：AI 报告 + 模拟志愿

- AI 报告：把结构化候选结果 + 学校趋势摘要作为上下文，通过 Prompt 工程生成个性化填报分析报告。
- 模拟志愿：用户排列志愿顺序，系统用贪心算法校验梯度合理性（冲稳保比例、前后志愿位次是否递减）。
- 可视化：ECharts 展示候选学校位次趋势、冲稳保占比、志愿梯度。

## 5. 技术选型（建议，可再讨论）

| 模块 | 选型 | 说明 |
| --- | --- | --- |
| 前端 | React 18 + TypeScript + Vite | 用户指定 React；TS 提升可靠性与答辩观感 |
| 前端 UI | Ant Design 5 | 表格/表单/仪表盘组件丰富，中文文档完善 |
| 前端数据 | TanStack Query + Axios | 服务端状态缓存、请求状态管理简洁 |
| 前端路由 | React Router 6 | 标准方案 |
| 可视化 | Apache ECharts（echarts-for-react） | 位次折线、冲稳保饼图 |
| 后端 | Python + FastAPI | 见下方「选型理由」 |
| 数据库 | SQLite（开发）/ MySQL（演示），SQLAlchemy 2.0 | ORM 统一，Alembic 做迁移 |
| 数据采集 | requests / httpx + BeautifulSoup / lxml + pandas | 静态页够用；JS 渲染页再上 Playwright |
| AI | DeepSeek（deepseek-chat，OpenAI 兼容协议）+ Mock 回退 | 真实接口，无 Key/断网时可降级演示 |

### 5.1 其余选型理由

**后端为什么选 FastAPI，而不是 Flask 或 Django**

1. 本项目后端本质是「数据 + 算法 + 调大模型」：爬虫清洗用 pandas、算法用 numpy/pandas、LLM 用 openai SDK，这些都在 Python 生态里最顺手，所以后端定 Python。
2. FastAPI 基于 Pydantic 做请求/响应校验，自动生成 OpenAPI 文档，前后端联调省很多沟通成本。
3. 它原生支持 async，调用 DeepSeek 这类 I/O 密集接口时更高效；Flask 的异步支持要绕路，Django 对这个轻量项目偏重。

**数据库为什么 SQLite + SQLAlchemy，而不是直接手写 SQL**

1. 开发期 SQLite 零配置，拷走即用，答辩演示不依赖外部数据库服务。
2. SQLAlchemy 让我们只写模型，开发用 SQLite、演示切换 MySQL 只改连接串；Alembic 管理表结构演进，避免手工改表出错。
3. 数据量级（几百所学校 × 5 年）用关系库足够，不需要上 MongoDB/ES。

**前端配套为什么是 TypeScript + Vite + Ant Design + TanStack Query**

1. Vite 是当下最快的 React 开发服务器，热更新快，写页面体验好。
2. TypeScript 让「考生画像、冲稳保结果、报告」这些数据结构有类型约束，和后端 Pydantic 模型对应，减少字段拼错。
3. Ant Design 内置表格、表单、步骤条、卡片，做「画像录入 → 候选列表 → 报告」这条流程最快；ECharts 用 echarts-for-react 包装，图表组件化。
4. TanStack Query 负责缓存接口数据、loading/error/refetch，比手写 useEffect + useState 更稳。

**爬虫为什么 requests + BeautifulSoup，而不是直接上 Scrapy**

1. 数据源一般是「按年份分页的学校录取表」，requests + BS4/lxml 足够覆盖，依赖少、好调试。
2. 清洗和入库用 pandas，和第二步算法共用一套技术栈。
3. 只有遇到「表格由 JS 动态渲染」的站点，才引入 Playwright 做兜底；Scrapy 框架对这个一次性采集任务偏重。

## 7. 核心算法（第一版规则，后续回测校准）

### 7.1 位次匹配度

以「最近一年最低位次」为主要参照，结合多年平均位次计算稳定值。

```text
rank_ratio = 学校参考位次 / 考生预估位次
冲：rank_ratio ∈ [0.92, 1.00)
稳：rank_ratio ∈ [1.00, 1.15)
保：rank_ratio ∈ [1.15, 1.35]
（阈值先给默认值，后经历史数据回测调整）
```

### 7.2 匹配分数

```text
match_score = w1·位次匹配度 + w2·城区契合度 + w3·住宿契合度
            + w4·历年稳定性 + w5·热度修正
```

### 7.3 模拟志愿贪心校验

1. 检查志愿是否按「冲 → 稳 → 保」的顺序排列，且参考位次总体递减。
2. 检查冲稳保比例（如 3:3:2 或 3:4:2，可配置）。
3. 对不满足梯度的地方给出提示与调整建议。

## 8. AI 报告设计

- 输入：考生画像 + 冲稳保候选清单（JSON）+ 各校近五年位次摘要。
- Prompt 结构：角色设定 → 背景数据 → 输出格式约束 → 风格要求（面向家长、避免夸大承诺）。
- 输出：个性化填报分析报告（Markdown），前端渲染。
- 降级策略：无 API Key 时用规则模板生成报告，保证系统可完整演示。
- 接入方式：DeepSeek 的 `deepseek-chat` 模型，走 OpenAI 兼容协议（`base_url=https://api.deepseek.com`），用 openai Python SDK 调用。
- 密钥安全：API Key 只放在后端 `.env`，通过环境变量读取，绝不硬编码进代码或提交到 Git；前端不接触 Key。

## 8.1 数据采集策略（补充）

1. 先确定数据源：优先找西安市教育局/招考网等官方发布的「各高中录取最低分/位次」公告页，其次用可信第三方汇总站交叉核对。
2. 采集脚本统一格式：`爬取 → 清洗 → 校验 → 入库`，每个数据源一个脚本，输出统一 CSV/结构化字段，避免脏数据污染知识库。
3. 合规与礼貌：限制请求频率、带 UA、只采集公开数据、用于课程学习；不采集个人信息。
4. 版本可追溯：记录 `source_url`、抓取时间，数据可复现、可回滚。

## 9. 开发路线图

- M1 基础框架：前后端骨架、数据库模型、示例数据种子。
- M2 知识库：采集/导入近五年数据，提供学校查询与位次趋势接口。
- M3 推荐引擎：画像过滤 + 匹配评分 + 冲稳保候选。
- M4 AI 报告：LLM 接入与 Prompt 迭代、Mock 回退。
- M5 模拟志愿：贪心校验 + 可视化大屏/报告页。
- M6 联调与答辩材料：演示脚本、测试用例、部署说明。

## 10. 风险与待确认问题

1. **数据来源是最大变量**：西安近五年中考投档位次数据能否拿到官方/可信渠道？还是先做模拟数据跑通全流程？
2. **AI 接入方式**：用真实大模型 API（OpenAI 兼容或国内模型），还是先做可切换的 Mock？
3. **技术栈最终形态**：前后端分离（Vue）还是单仓库模板方案？
4. **位次口径**：使用全市位次还是分区位次？这会影响冲稳保阈值设计。

## 11. 特长生（体育类 / 艺术类）筛选设计

### 11.1 背景与关键判断

招生计划 PDF 中每所学校带有「特长生招生项目」，分体育类和艺术类，例如：

- 体育类：田径、篮球、足球、排球、游泳、击剑、射击、射箭、乒乓球、羽毛球、棒（垒）球、举重、武术、健美操、围棋等。
- 艺术类：美术、书法、舞蹈、声乐、器乐、戏剧（曲）等。

但特长生录取与文化课统招是两套规则：2025 年城六区普通高中录取控制线 611.0 分，体育、艺术特长生控制线 366.6 分，按「专项测试 + 文化课过线」录取。因此：

1. 特长生筛选不建议直接套用现有「位次冲稳保」算法，位次参考意义较弱。
2. 更合理的做法是给特长生一个相对独立的查询视图，弱化位次、强化「是否有该项目、学校层次、录取线」。

### 11.2 数据层

新增一张规范化表 `school_talent`：

```text
school_talent
  id, school_id, category(体育/艺术), item(田径/篮球/美术/舞蹈/...)
```

来源：解析 `data/raw/2025城六区公办招生计划.pdf` 和 `2025城六区民办招生计划.pdf` 的「特长生招生项目」列。

### 11.3 筛选交互（草案）

在考生画像中增加：

- 特长方向：不限 / 体育类 / 艺术类。
- 特长项目：选择方向后出现多选，如体育类→田径、篮球、足球……，艺术类→美术、舞蹈、声乐……。

匹配规则：用户选了具体项目后，只保留 `school_talent` 中命中该项目的学校；未选则不过滤。候选列表和趋势详情中展示该校的特长项目标签。

### 11.4 与冲稳保的关系（待确认）

- 方案 A：特长生作为「统招冲稳保」之外的独立「特长生学校查询」模块，不参与位次计算。
- 方案 B：作为统招筛选的附加硬条件，但界面明确提示「特长生录取线不同，位次仅供参考」。
- 方案 C：两者都做：默认方案 A，同时在统招结果里把特长项目作为展示标签。

倾向推荐方案 A 或 C。
